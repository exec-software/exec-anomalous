# ADR 0031: Add an interactive bootstrap desktop development image

- Status: Proposed
- Date: 2026-09-26

## Context

The accepted native display proofs terminate after their verified frame. They
are useful evidence, but do not let a person keep a desktop open while testing
the next changes. Deploying the persistent semantic service still requires
private writable vessel state, authenticated cross-process presentation,
service supervision, and integration of ADR 0030's recovery boundary.

A bounded development launcher can provide an interactive test loop now,
without treating those missing facilities as implemented.

## Decision

Add the opt-in `desktop_dev` kernel feature and a separate
`build/desktop-dev.img`. Threshold remains the loader. The ordinary image and
the accepted terminal proof commands retain their behavior. When unrelated
terminal proof flags are combined with `desktop_dev`, the existing terminal
proof precedence wins; the all-features build must not become an interactive
launcher.

### Render once before external interrupt initialization

Use the same separately linked native source and isolated ring-3 renderer as
ADR 0029, with its exact redacted ordinal-61 body, copied transport, private
full-frame staging, framebuffer readback, and complete native teardown. Do
not introduce a kernel semantic rasterizer or map the framebuffer into ring 3.

The development entry runs while the external interrupt backend is still
uninitialized, IF is clear, and both PICs are masked. An explicit runtime
bootstrap mode preserves that virgin backend through the native continuation;
the terminal proof and every failure path retain terminal interrupt shutdown.
After the unique presenter has gone away, restore the diagnostic framebuffer
registration. Initialize external interrupts exactly once, using the ordinary
keyboard and PIT path. Do not rerun the native proof under live interrupts.

### Keep one public frame and a bounded interactive loop

Retain one feature-only, bounded copy of the verified public framebuffer in
kernel storage. Validate the full aperture before copying; include scanline
padding, and refuse unsupported geometry. This buffer is never mapped into a
vessel and never captures a shell session. Its reserved kernel storage remains
outside the allocator's free pool. Exclusive BSP ownership serializes the
cache, console, and framebuffer operations.

The initial launcher has one enabled, focused primary action, **Open shell**.
Enter opens the existing kernel-hosted bootstrap shell. Only its returning
development session recognizes `desktop`, drops the shell console, and restores
the complete cached frame. Repeated open/return cycles must work without a
reboot. The normal shell retains its five commands. Existing keyboard loss,
source reinitialization, and stale-input handling remain in force. After
returning or input loss, activation waits for Enter release before accepting a
new press, so a held submit key cannot immediately reopen the shell.

This is an explicit temporary bootstrap UI policy in a removable feature.
There is no mouse, window manager, dynamic scene mutation, general focus
transfer, or live accessibility/machine action service. The disabled secondary
control stays disabled. Removing the feature removes this launcher policy and
cache; the future supervised user-space service replaces them.

### Keep evidence attributable and private

`desktop-image`, `desktop-run`, and `desktop-smoke` package and inspect the same
native payloads while writing a separate disk image. An interactive run copies
the inspected disk into a unique private run directory before releasing the
shared build lock and launching QEMU. Later
builds can proceed without modifying the running VM's disk or logs. The run's
image is removed only after its child is reaped; bounded private logs remain
available for diagnosis.

The fixture is generated by the existing host transaction builder, but the
launcher does not call its semantic publication completion path or claim a
deployed native transaction.
Native presentation events attest native rendering and copy, not host service
publication. The existing accepted ADR 0029 command keeps its strict retained
transaction verifier and completion path.

The development transcript has its own actual order: boot, native
presentation, interrupt initialization, launcher readiness, and bounded shell
transitions. Static command kinds and sequence numbers are observable; typed
command text, echoed data, and private source bodies are not. Interactive
serial logs are private files. Smoke captures are retained only after the
public desktop oracle matches every pixel. Do not retain shell screenshots.

## Validation and rejection criteria

Require host checks for feature selection, cache bounds, returning-command
gating, and malformed, reordered, or private transcript rejection. The QEMU
development smoke must verify the initial native frame, Enter activation,
edited shell input, private echo redaction, exact desktop restoration, a second
open/return cycle, and a still-running child. Failures clean up only the owned
QEMU child and reject incomplete evidence. Normal-image exclusion must cover
development symbols and markers. Run the full existing regression matrix and
exercise VirtualBox where supported.

Reject this approach if it weakens terminal failure containment, reinitializes
the interrupt backend, adds a concurrent framebuffer writer, caches private
shell pixels, changes the ordinary shell, or claims semantic publication from
presentation-shaped evidence. Observed evidence belongs in the linked
development log, rather than being assumed by this proposal.

## Alternatives and consequences

Continuing only with terminal frame demos delays interactive feedback. Shipping
the complete native service first would combine several unproved privilege and
lifecycle boundaries in one change. A new kernel rasterizer would duplicate
scene policy and renderer behavior. The selected intermediate mode reuses the
proved native rendering path and the existing bootstrap shell, at the cost of
a feature-only framebuffer cache and explicitly temporary launcher policy.

This does not accept a production desktop, service-loss recovery, atomic
scanout, a graphics ABI, or a normal-image desktop. ADR 0030 and the native
service roadmap remain separate work.
